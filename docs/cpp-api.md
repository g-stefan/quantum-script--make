# C++ API

The C++ side of this extension is small: `Make` is implemented in Quantum
Script (`Make/Library.js`) and the native library only compiles that source
into the executive. Read the `quantum-script` repository's
`docs/embedding.md` first for hosts and init callbacks.

## Headers and namespace

```cpp
#include <XYO/QuantumScript.Extension/Make.hpp>   // Make/Library.hpp

using namespace XYO::QuantumScript;
```

Namespace: `XYO::QuantumScript::Extension::Make`. Export macro:
`XYO_QUANTUMSCRIPT_EXTENSION_MAKE_EXPORT` (empty when
`XYO_QUANTUMSCRIPT_EXTENSION_MAKE_LIBRARY` is defined, i.e. static builds).

## Registering the extension

```cpp
void Extension::Make::registerInternalExtension(Executive *executive);
void Extension::Make::initExecutive(Executive *executive, void *extensionId);
```

- `registerInternalExtension` registers `"Make"` as an internal extension;
  call it from the host's init callback (see
  [Getting started](getting-started.md#4-register-it-in-a-c-host)).
- `initExecutive` is the extension's init function, run by the engine when a
  script first requires `Make` in a thread. It sets the extension name,
  info (`"Make"` and the short license text), version and marks it public,
  then runs `executive->compileStringX(librarySource)`. Do not call it
  directly.
- The DLL build also exports
  `extern "C" void quantumScriptExtension(Executive *, void *)`, which
  forwards to `initExecutive`; it is what `Script.requireExtension` looks up
  in `quantum-script--make.dll`.

## Extensions the host must provide

`Library.js` starts with:

```javascript
Script.requireExtension("Thread");
Script.requireExtension("Shell");
```

so a host that registers `Make` as internal must also make `Thread` and
`Shell` loadable (internal, or as DLLs next to the engine DLL), plus what
they load in turn (`Buffer`, `ShellFind`). Every recipe runs on a thread
whose executive is created with the host's init callback
(`ExecutiveX::initExecutive(..., applicationInitExecutive)`), so the
extensions recipes require (`Console`, `File`, `JSON`, ...) must be
registered there too.

| Host | Recipes can load |
|------|------------------|
| `quantum-script` interpreter | every `quantum-script--*.dll` in the SDK `bin` folder |
| `fabricare` | every extension fabricare registers (Console, Application, Buffer, DateTime, JSON, File, Shell, ShellFind, Math, ProcessInteractive, SHA512, Thread, Task, Job, Make, CSV, URL, ...) |
| your host | what its init callback registers |

## The embedded script

`Make/Library.Source.cpp` holds `Library.js` as
`static const char librarySource[]`, generated by
`fabricare/make.prepare.js`:

```
file-to-cs --touch=Library.cpp --file-in=Library.js --file-out=Library.Source.cpp --is-string --name=librarySource
```

`--touch=Library.cpp` updates the time of `Library.cpp`, which includes the
generated file, so the next compile picks up the change. Always edit
`Library.js` and rebuild; never edit `Library.Source.cpp` by hand.

## Calling `Make` from C++

There is no C++ class: drive a build by running script code.

```cpp
if (!ExecutiveX::executeString(
        "Script.requireExtension(\"Make\");"
        "var make = new Make();"
        "make.target(\"out.txt\", \"in.txt\", function(target, source) {"
        "	Script.requireExtension(\"Shell\");"
        "	return !Shell.copyFile(source, target);"
        "});"
        "make.build(\"out.txt\");")) {
	printf("%s\n", (ExecutiveX::getError()).value());   // e.g. "Make: Source not found: in.txt"
};
```

## Notes for maintainers

- Keep `Library.js` in the Quantum Script dialect (see the `quantum-script`
  repository): `typeof(x)` with parentheses, statements and blocks end with
  `};`, no `let` / `const` / arrow functions.
- Declare every local with `var`: an undeclared variable assigned in a
  `Make` method is a global of the calling script.
- `buildTreeGenerateTarget_` on a target already visited in this build
  bumps its sources one level below the current one and returns whether
  the target is already in the build tree (`buildTreeHasTarget_`), so every
  dependent of a scheduled shared dependency is rebuilt too, and the
  dependency is added on the dependent's level + 1.
- Recipes are started by `buildThread_`, which throws
  `Build failed, unable to start recipe: <target>` when `Thread.newThread`
  returns `null`.
- `test/test.01.js` only loads the extension; `test/test.02.js` builds
  diamond graphs in `temp/test.02` (a shared dependency reached on the same
  level and on different levels) and checks that a global `k` survives
  `build`. Extend it when changing the build logic.
